Chasse aux bugs

Audit de correction réparti sur 4 sous-systèmes, chaque bug relu dans le code réel avec un scénario de déclenchement concret. Aucune supposition — seulement des bugs confirmés.

⚠ Le motif qui revient

Plusieurs détections sont silencieusement mortes : un wrapper _get() renvoie un dict, mais la fonction y accède en attributs (response.status_code) → AttributeError avalée par un except → retour None. Les tests unitaires ne l'attrapent pas car ils n'assèrent que le type du retour, jamais la détection effective d'une vuln. Résultat : l'outil paraît fonctionner mais rate de vraies vulnérabilités.

Haute — faux négatifs & fuites
cors_tester.py:157faux négatif
Détection CORS (réflexion d'origine, bypass, vary) entièrement morte : response.headers sur un dict. Une réflexion Origin: evil.com + credentials: true (CVSS 9.8) n'est jamais signalée.
graphql_scanner.py:94 · websocket_scanner.py:62faux négatif
Lecture har_data['entries'] au lieu de har_data['log']['entries'] → 0 endpoint détecté sur tout HAR réel. Le scan GraphQL/WebSocket est toujours vide.
jwt_attacks.py:411faux négatif
Attaque KID injection morte : response.status_code sur un dict. Un path-traversal kid=../../dev/null (secret vide) réussi n'est jamais détecté.
zap_fuzzer.py:113faux négatif
return placé dans la boucle for param in id_params → le fuzzer IDOR ne teste que le premier paramètre. Sur ?user_id=1&doc_id=5, doc_id (souvent le vrai vecteur) est ignoré.
docker_manager.py:42fuite ressource
start_zap() crée le conteneur puis _wait_for_zap() peut lever TimeoutError sans l'arrêter. Sur le chemin app.py (sans finally), chaque échec empile un conteneur orphelin.
har_preprocessor.py:70état accumulé
process() fait des .append() sans réinitialiser l'état. Enchaîner print_summary() puis save() double les données extraites (et mute rétroactivement le 1ᵉʳ résultat, passé par référence).
Moyenne — logique & calibrage
acceptance_engine.py:188CI · faux échec
Précédence d'opérateur dans _check_no_xss : and lie plus fort que or, donc la garde de risque ne couvre pas la clause 'xss'. Une alerte XSS en risque Low fait échouer le build à tort (le pendant SQL est correct).
owasp_mapper.py:196CI · faux succès
cweid (chaîne côté ZAP) comparé à une liste d'entiers → match par CWE mort. Une alerte High mappable seulement par CWE tombe en « unmapped » et ne fait pas échouer le verdict OWASP.
llm/context_extractor.py:228cache · collision
Clé de cache LLM = nombre d'entrées + chemins, sans le domaine. Deux hôtes de même structure (api.foo.com/api.bar.com) → le 2ᵉ scan reçoit le plan d'attaque du 1ᵉʳ.
adaptive_tuner.py:85code mort
fp_count > 5 alors que le compteur ne monte que de +1 par appel, appelé une seule fois. Tout le réglage adaptatif anti-faux-positifs ne se déclenche jamais.
redteam_attacks.py:313faux positif
Mass assignment signalé sur simple « 2xx sans "error" ». Un 204 No Content qui ignore le champ role:admin est faussement rapporté comme escalade acceptée (confiance 0.7).
cache_poisoning.py:204faux positif
Le même jeton rand sert de cache-buster (?cb=rand) et de marqueur. Toute appli qui reflète la query string (lien canonique, og:url) déclenche un faux « cache poisoning » à confiance 0.9.
idor_detector.py:222faux nég. + faux pos.
La bande de ratio [0.1, 0.5) tombe sur le return « faux positif » final (un IDOR à ressource plus petite est raté). Et le fallback suit les redirections → un 302→login peut passer pour VULNERABLE.
payload_analyzer.py:299 · payload_reconstructor.py:189code mort
isinstance(v, int) testé avant isinstance(v, bool) ; comme bool hérite d'int, les branches booléennes sont mortes → un booléen est étiqueté _INT et le juggling bool→int n'est jamais généré.
token_extractor.py:206faux positif
'id' in param_lower matche width, hidden, provider… → des valeurs non-identifiantes polluent la wordlist d'IDs qui alimente l'IDOR.
zap_http_client.py:97requête mal formée
Content-Length: len(body) compte les caractères, pas les octets UTF-8. Un corps accentué (montant=déjà payé) annonce une taille trop courte → tronqué côté serveur.
zap_scanner.py:245blocage
while spider.status < 100 sans borne temporelle (contrairement aux autres _wait_*). Un spider gelé à un statut stable boucle indéfiniment en plein pipeline synchrone.
Basse — bruit, robustesse, reporting
reporter.py:200 — empreinte SARIF via hash() natif (salé par process) → non déterministe entre runs, suivi GitHub Code Scanning cassé.
llm/analyzer.py:116 — un plan LLM vide (échec de parsing) est mis en cache 24 h → tous les runs suivants sur ce HAR ne réessaient pas.
passive_analysis.py:321 — seuil d'entropie < 4.0 par caractère → quasiment tout token hex de 32 car. (128 bits, solide) faussement « Weak Token ».
zap_passive_scanner.py:188 — seuil session_id = 4.5 par symbole, inatteignable (max log2(16)=4.0) → faux positif garanti sur tout token ≤ 22 car.
redteam_attacks.py:449 — hidden param détecté sur diff > 100 octets contre une baseline unique → faux positif sur page dynamique (CSRF, timestamp).
http_smuggling.py:172 — '400' in resp and '200' in resp matche n'importe où (corps inclus) → faux « smuggling » Critical sur du JSON contenant ces chiffres.
jwt_attacks.py:262 — « none algorithm » ne teste que la longueur (le commentaire promet une similarité) → faux positif si l'API renvoie 200 {"error":...}.
findings_store / fp_store — clé de dédup sans param → deux alertes du même plugin sur des params différents fusionnées, une vuln perdue.
payload_reconstructor.py:58 — _set_nested_value lève TypeError si un segment de chemin chevauche un champ scalaire ({"user":"bob"} + user.id).
parse_qs sans keep_blank_values (har_analyzer, har_preprocessor, token_extractor, har_diff) → params vides ignorés (?redirect= open-redirect manqué).
payload_analyzer.py:121 — off-by-one sur frequency : compteur créé à 1 puis incrémenté à la création → toujours occurrences + 1.
zap_http_client.py:313 — filtre get_alerts(risk) passe une chaîne ('High') là où ZAP attend un riskid entier 0-3 → filtre incohérent.

Deux bonnes nouvelles vérifiées : la logique pass/fail CI de AcceptanceEngine.evaluate n'est pas inversée, et correlator, webhook_sender (HMAC), meta_analyzer, script_manager, trainer sont sains. Le risque n'est pas dans le socle — il est dans des détections qui échouent en silence.
